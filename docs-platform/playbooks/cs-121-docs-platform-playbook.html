The platform that tells you where the docs disagree

Round one chose the platform; Fumadocs inside the app is built and working. This is the build scope for round two. Every capability the research called for still stands — what's added is the feature that makes this worth a scraper developer's attention: the platform compares its input sources, reports where they disagree, and names the CTD developer who owns that path. It never resolves the disagreement itself. A human routes the correction upstream and nothing merges until it's settled. Section 00 is the framework contract; section 02 is the main build.

00What the framework defines

Read this first. It's the contract Fumadocs imposes on this app — the directory it reads, the frontmatter fields it validates, the file that controls navigation, and what one source file becomes at build time. Everything here is taken from fumadocs-core@16.15.1's own schema, not from convention or preference.

One directory, and it's configured in one line

source.config.ts declares the content root. This is the single fact everything else follows from: 

// source.config.ts
export const docs = defineDocs({
  dir: "content/docs",   // the only directory compiled
});

lib/docs-source.ts then maps that collection to a URL prefix via loader({ baseUrl: "/docs" }). Files outside content/docs are not compiled, not routed, not indexed — regardless of extension or location in the repo. A .mdx file anywhere else is an ordinary file on disk.

The frontmatter schema — exactly four author-facing fields

Fumadocs validates every page against pageSchema. The full set, from fumadocs-core/dist/source/schema.d.ts:

Field Type Required What the framework does with it
title string Yes Sidebar label, <DocsTitle>, and <title> via generateMetadata. Independent of any # heading in the body.
description string No <DocsDescription>, the meta description, and the search-result snippet.
icon string No Resolved by an icon handler you supply to loader(). Not wired up in this app yet.
full boolean No Renders the page full-width, suppressing the right-hand TOC column.

(_openapi is the fifth key and is reserved for fumadocs-openapi's generator — not hand-authored.) Unknown keys are stripped rather than rejected, so a typo in a field name fails silently: the value is dropped and the page renders without it. 

---
title: Any page title          # required — omit it and the build fails
description: One sentence.     # optional, but it's the search snippet
---

# Body starts here

meta.json — the navigation contract

A folder's meta.json is validated against metaSchema. It controls the sidebar; it has no effect on routing. Eight fields:

Field Type Effect
title string The folder's label in the sidebar.
pages string[] Which children appear, and in what order. Array order is display order.
description string Shown under the folder title in some layouts.
root boolean | string Marks the folder as a root — a separate top-level docs tree, which is how a sidebar tab / section switcher is created.
defaultOpen boolean Folder starts expanded.
collapsible boolean Whether the reader can collapse it at all.
pagesIndex string Which child acts as the folder's own landing page.
icon string Same icon handler as page frontmatter.

The pages array accepts five operators, not just filenames

This is the part worth knowing before hand-listing every page forever. From the page-tree builder's own source:

Syntax Meaning
"page-name" A file or folder, by slug.
"..." Rest — every remaining child not named explicitly. "z...a" does the same in reverse order.
"!page-name" Exclude — keep the page routable but hide it from the sidebar.
"...folder-name" Extract — flatten a subfolder's children into this level.
"---Label---" A non-clickable separator heading. Bare "---" is a plain rule.
"[Label](/url)" An arbitrary link; prefix external: for off-site.

So a folder that should just list everything alphabetically needs no maintenance at all: 

{
  "title": "Section name",
  "pages": ["index", "---Reference---", "..."]
}
Omitting meta.json is a real choice, not an oversight

With no meta.json, Fumadocs falls back to listing the folder's children automatically. A file left out of an existing pages array, however, stays routable and searchable but never appears in the sidebar — which in practice means nobody finds it. Either list it, or use "..." so new files are picked up by default.

Filename determines URL; nothing else does

app/(docs)/docs/[[...slug]]/page.tsx resolves a request through source.getPage(slug), where the slug comes from the file's path under content/docs. So:

File URL
content/docs/index.mdx /docs
content/docs/<folder>/index.mdx /docs/<folder>
content/docs/<folder>/<name>.mdx /docs/<folder>/<name>

Renaming a file changes its URL and breaks inbound links. A folder becomes a sidebar group; its index.mdx becomes that group's landing page.

What one file becomes at build time

Four outputs, all automatic once the file is in content/docs with valid frontmatter:

1

A route

Statically generated via generateStaticParams() over source.getPages().

2

A sidebar entry

Placed by the page tree, labelled from frontmatter title.

3

A search record

Indexed through app/(docs)/api/search/route.ts.

4

An LLM entry

Emitted into /llms.txt and /llms-full.txt.

A right-hand table of contents is derived from the body's ## and ### headings via page.data.toc — so structure the body with real headings, not bold lines.

Extending it: MDX components

components/docs/mdx.tsx is the extension point. Anything registered in getMDXComponents() is available in every page with no per-file import — the app already does this with <StatusChip>: 

// components/docs/mdx.tsx
export function getMDXComponents(components?) {
  return {
    ...defaultMdxComponents,   // Callout, Tabs, Steps, Accordion…
    StatusChip,                // your own, usable in any .mdx
    ...components,
  };
}

This is what makes docs-in-the-app worth the coupling: a page can render the application's real components rather than a screenshot of them. Every component proposed in section 04 registers here.

The contract in one sentence

Put an .mdx file under content/docs/ with a title in its frontmatter, make sure its folder's meta.json either names it or ends with "...", and the build produces a route, a sidebar entry, a search record, and an llms.txt line.

Notation — planning only, never shipped

The § shorthand throughout this playbook is a drafting convention for cross-referencing source documents and this playbook's own sections. It must not survive into the built site: no § in any MDX page, heading, nav label, or component. Published pages name their source in prose ("per the Development Guidelines, Meeting schema") and link to headings by anchor. Section numbers also collide by coincidence between documents — where the source isn't obvious from the sentence, this playbook names the document explicitly.

Glossary

CTD = Code the Dream, the apprenticeship organization that builds and maintains the scrapers and this Meetings Viewer repo. PDW = Public Data Works, the partner engineering/design studio that operates Documenters.org and its data pipeline. CB = City Bureau, the partner org that runs the Documenters civic-journalism program and does editorial/data QA on scraper output. These three abbreviations recur throughout this playbook without re-expansion after this point.

01Scheduling the original calls

The original research chose four capabilities. None are dropped here. What this section adds is when each lands and what it has to be sized against — because a capability shipped in the wrong order becomes an obstacle rather than a benefit, and the goal of this round is that a scraper developer feels the platform save them time, not cost them any.

1.1 Keystatic — a platform capability, scheduled for P4

An editing surface that doesn't require a terminal is a property of the platform, independent of who ends up using it. It mounts as an admin route inside this app, needs no separate deployment, and its free tier requires only that an editor hold repository write access.

It lands in P4 rather than earlier for a build reason, not a political one: Keystatic's editor writes whole files, so a page that imports a live component cannot be edited through it without risking the import. That constraint is only knowable once the component set in section 04 exists. Building the editor first would mean retrofitting the restriction afterwards.

One thing to verify in the spike, not assume

Whether an edit commits directly to a branch or opens a pull request is undocumented, and it determines whether edits made through the editor pass through the conflict reporter in section 02 at all. Test it before the phase is estimated — if edits bypass CI, the editor and the reporter need wiring together.

1.2 The CI quality gates — sized to the platform, sequenced to stay green

Vale, cspell, lychee, axe-core and Lighthouse CI all stay. One scoping correction to state plainly: these are platform quality gates, and sizing them against how many pages currently exist is the wrong measure. Accessibility and performance budgets don't become worthwhile at some page count — they're either part of the definition of done or they aren't.

What matters is adoption order. Each gate is introduced in a state where it passes on the existing corpus, then tightened:

Gate Catches Lands green by
Build + internal link/anchor check Broken MDX, dead cross-references Being deterministic — it either resolves or it doesn't
cspell Typos, including in code identifiers Running on changed files only at first
lychee External link rot Scheduled, reporting to an issue — never blocking a PR on someone else's downtime
Vale Prose-style drift across authors Commenting on the diff only, with a project vocabulary seeded first
axe-core Accessibility violations Being genuinely deterministic — this is the one that should block
Lighthouse CI Performance regressions Median of three runs, warning-only — shared runners are too noisy to gate on

1.3 Drift detection — promoted, not replaced

The original research proposed piloting drift detection — tooling that notices when a page and its source stop matching. The tempting counter-proposal is to skip the detector and generate the drifting page instead: render qa/schema.mdx straight from the types in lib/scraper-data.ts, and the page can never disagree with the code because the page is the code, formatted.

That is a false choice, and the reasoning behind it is wrong in a way worth naming: it treats drift as a content-quality problem to be designed away, when detecting drift is the platform's product. The disagreements that actually cost a scraper developer trust aren't ones this repo can generate away — a CTD page, a PDW document, and city-scrapers-core's constants.py saying three different things live in sources this app can't write to.

Generation and detection do different jobs. Generation eliminates drift where this repo owns both sides — a page rendered from a type in this codebase cannot disagree with it. Detection is the only option everywhere else, which is most places: sources owned by other teams, in other repositories, in documents this app can't write to. Section 02 is that capability, and it's the main build of round two.

Detection alone would be noise, so section 02 also specifies what the reporter does with a finding: it records the exact claim, both sources' values, a confidence class, and the owning developer resolved from CODEOWNERS — then surfaces it as a PR comment at the moment of change, a dashboard row as standing state, and a JSON record an agent can act on. A human routes the correction upstream; the platform never resolves it.

1.4 Diagrams — match the form to the content

No disagreement with the original research here; both say the same thing. Linear processes render as MUI's Stepper, which is already a dependency and inherits the app's own visual system. Actual graphs — data flows, trust boundaries — are hand-authored SVG or Mermaid. The distinction is the content's shape, not a blanket preference for one tool.

Why this ordering serves a scraper developer

P1 and P2 deliver something that saves time immediately: a docs site that looks like the app, and a reporter that tells them when a page they're about to trust disagrees with the code. The editing surface and the heavier gates arrive after, once the thing they'd be gating actually exists. Nothing in the first two phases asks a developer to learn a new process.

02The conflict reporter

This is the platform's distinguishing feature and the main build target of round two. Everything else on this site is a docs site; this is the part that earns the docs site a place in a scraper developer's workflow instead of adding to it.

The contract, stated once

The platform detects that two sources disagree, locates the disagreement precisely, and notifies the CTD developer who owns that path. It does not decide who is right, does not edit anyone's source, and does not silently correct a page. A human routes the correction upstream to CTD's internal team, PDW, or whoever owns the source; a CTD manager merges once it is settled.

2.1 Why a docs platform is the right place for this

A scraper developer's real cost isn't finding documentation — it's trusting it. When the same fact appears in four documents owned by three organizations, the developer either checks all four (slow) or picks one and hopes (wrong). Both outcomes make docs a tax rather than a tool.

Because this site already ingests every one of those sources to publish them, it is the only place in the program that holds them side by side. Detecting the disagreement is nearly free once the ingestion exists; the value is entirely in routing it to a person who can act.

2.2 The five source classes and what can be checked

Every page traces to a source, and the source class determines what kind of check is even possible. This is the taxonomy the reporter is built on:

Class Example source Machine-checkable? Check performed
Executable A constant, type, or schema in code Fully Parse it and compare against what the page publishes. Highest confidence — code is the arbiter.
Structured A JSON fixture, a config file Fully Shape and value comparison against the documented contract.
Git-owned prose An MDX page in this repo Partly Internal links, anchors, referenced symbols still existing, staleness vs. its cited source.
Synced prose A document this team can write to Partly Revision drift: has the upstream moved since the page was generated from it?
External prose A document owned by another org Barely Reachability and a freshness clock only. No content comparison is possible without a machine-readable source. A page that restates one's substance carries a provenance line and a short freshness clock — asking the owning team for a named contact is a courtesy, not a gate.
Confidence must be visible, not implied

A reported conflict between a page and executable code is a near-certain defect. A reported staleness on an external document is a prompt to go ask someone, and may be a false alarm. If the reporter presents both with the same weight, developers learn to ignore it — the single most likely way this feature fails. Every finding carries its class and its confidence.

2.3 Routing: who gets told

Detection without routing is just a longer build log. The platform resolves each finding to a person using CODEOWNERS, which GitHub already reads natively — no bespoke ownership registry to maintain alongside it.

Verified — three constraints that shape the design

Checked against GitHub's own documentation, because each one breaks routing silently if missed:

  • A code owner must have explicit write access to the repository, even via a team. Listing someone without it fails quietly — no request, no error.
  • The CODEOWNERS file must exist on the base branch of the pull request, not just on the feature branch.
  • Three gitignore behaviours do not work: ! negation, [ ] character ranges, and backslash-escaping a leading #. Patterns relying on them silently match nothing.

Two further behaviours are useful rather than hazardous: review is requested automatically without branch protection, so routing works from day one; and draft pull requests don't trigger requests until marked ready, which conveniently suppresses noise while work is in progress.

This repository has no CODEOWNERS file today, so routing currently has nothing to resolve against. Creating it is the first task of this section, and it is a single file.

Ownership is per-path, and it is about routing, not permission

An entry says "when something under this path is in question, ask this person first." It does not restrict who may author a change. The practical shape, given that merges on this repo are currently performed by a small number of people: 

# .github/CODEOWNERS — on the base branch
# Paths are routing addresses, not access controls.

/content/docs/                 @ctd/docs-maintainers
/components/docs/              @ctd/docs-maintainers
/.github/workflows/            @ctd/platform

# Narrower paths win — the LAST matching pattern applies,
# so put specific overrides below general ones.
/content/docs/scrapers/        @ctd/scraper-leads

2.4 What a report looks like

One finding, rendered three ways from the same record: a PR comment for the moment of change, a dashboard row for the standing view, and a structured record so an agent can consume it.

The platform's responsibility ends at naming the right person. Correction happens in a conversation between teams, upstream, and nothing merges until it has.

The finding record

One shape, so the PR comment, the dashboard, and any agent all read the same thing: 

{
  "id":          "stable-hash-so-it-can-be-muted",
  "claim":       "what the page asserts",
  "sources": [
    { "ref": "path-or-url", "class": "executable", "value": "..." },
    { "ref": "path-or-url", "class": "git-prose",   "value": "..." }
  ],
  "confidence":  "certain | likely | prompt",
  "owner":       "resolved from CODEOWNERS",
  "blocking":    true
}

id being a stable hash is what makes the feature survivable: a finding a developer has judged to be a false positive can be muted once and stay muted, rather than reappearing on every build until they stop reading the output.

2.5 What blocks a merge, and what only informs

This is the setting that decides whether developers experience the platform as help or as an obstacle. The rule follows confidence, not severity:

Confidence Meaning Behaviour
certain A page contradicts an executable source Blocks the merge. Code is the arbiter; there is nothing to debate.
likely Two prose sources disagree, or a cited symbol is gone Comments on the PR and requests the owner's review. Does not block — a human decides.
prompt An external source is stale or unreachable Dashboard row and a periodic digest only. Never touches a PR.
Start with nothing blocking

Ship every class as non-blocking for the first two weeks and watch the false-positive rate. Promote certain to blocking only once it has been quiet on real pull requests. A gate that is red on the day it lands gets disabled, and the feature never recovers.

2.6 Proving it works before trusting it

The reporter needs a test corpus with known disagreements in it — documents where the answer is already established, so a missed detection is visibly a bug rather than an open question. The program's existing source documents serve this purpose well: they contain real, naturally occurring inconsistencies across several organizations' material.

Two things this fixture set is for, and one it is not:

  • Recall — of the disagreements a human reviewer can find by reading, how many does the reporter surface?
  • Precision — how many findings does it raise that a developer would judge to be noise? This number governs whether anything is ever allowed to block.
  • Not a backlog of content to fix. The fixtures exist to exercise the detector. Whether any particular statement in them is correct is a question for the owning team, later.
Acceptance criterion for this section

A developer opens a pull request touching a documentation page. Within the CI run, they see a comment naming the exact claim, the two sources that disagree, which one is authoritative, the confidence, and the CTD developer to talk to — without having opened any of the source documents themselves.

The pipeline diagram missed a mode — corrected, then confirmed

It would be easy to draw the Meetings Viewer as never touching production and stop there. The viewer reads it via plain raw.githubusercontent.com URLs under a /pr/{repo}/{pr_number}/scrapers route — no backend, no database, no auth on the read side (§7's architectural invariants are explicit about this). Same UI, same components, same routes as local mode — only lib/scraper-data.ts's implementation changes (§5.2). That mode doesn't touch Documenters.org's Azure/ETL/Postgres pipeline either, but it's explicitly meant to be used during PR review — which means by PDW and CB, not just by a CTD apprentice at their own keyboard. 04UX / UI system for the content

This is the part the original research under-weighted and this playbook doesn't: the platform choice and the CI checklist are both in service of pages people actually want to read. Two things need to happen before the new content lands — one fix, one small component set — plus a few standing rules for every page after.

4.1 Ship the theme mapping that was always the plan

globals.css currently only imports Fumadocs' stock neutral.css preset — none of the --color-fd-* → --mui-palette-* mapping from the original research's §8 was ever added. Dark mode switching works (DarkModeSync correctly drives Fumadocs' .dark class off MUI's color scheme), but /docs is still rendering in Fumadocs' generic gray, not the app's own palette. 4.3 Standing rules for every page from here on

  • One repo-scope callout on any page describing the scraper repos, placed above the fold — never assume the reader knows which codebase a command runs against.
  • Commands are copy-pasteable as written. The guide is precise about flags that matter (-O not -o, pipenv run prefixes) — docs must never round that off for brevity, since the flag itself is the QA lesson.
  • Good/bad example pairs (already used well for title formatting) become a recurring pattern, not a one-off — it's the exact shape a reviewer scans for.
  • Dark mode + MUI parity checked before merge on every new docs page — keep this as a standing PR habit, not a one-time P0 spike item.

05Automation

There is no CI for the docs in this repo today — no .github/workflows directory at all. Five workflows are in scope for round two. The first implements section 02; the rest are the original research's quality gates, introduced in an order where each lands passing.

W-1P2

docs-conflict-report.yml

The main build. Runs the comparators from section 02 across the source classes, emits one finding record per disagreement, resolves the owner through CODEOWNERS, and posts a PR comment. Writes the same findings as a JSON artifact for the dashboard and for agents.

Non-blocking on arrival. Only certain-confidence findings are ever promoted to blocking, and only after the false-positive rate has been observed on real pull requests.

W-2P5

docs-build.yml

next build plus an internal link and anchor checker walking source.getPages(). Deterministic — a link either resolves against a real page and heading or it doesn't — so this one can block from day one.

W-3P5

docs-prose.yml

cspell on changed files, then Vale once a project vocabulary is seeded. Both report on the diff rather than the whole corpus, so adoption doesn't begin with a wall of pre-existing findings. Vale's style packages should be pinned to a release rather than tracked, so an upstream rule change can't fail an unrelated PR.

W-4P5

docs-links-external.yml

lychee, on a schedule rather than per-PR, opening a single rollup issue. External link rot has nothing to do with the pull request that happens to be open — blocking a developer on another site's downtime is how a check earns a reputation for wasting time.

W-5P5

docs-quality.yml

axe-core for accessibility — deterministic, and the one quality gate that should block. Lighthouse CI alongside it for performance and SEO, as a warning only and on the median of three runs; shared CI runners are too noisy to gate on, and a flaky performance gate gets removed within a month.

Where generation fits

Pages rendered from a source this repo owns — a type, a constant — can't drift by construction, so they need no check. Where a generated file must be committed, the pattern is: regenerate in CI and fail if git diff is non-empty. That's narrower than section 02's reporter and complements it: generation removes the possibility of drift where we control both sides, detection covers everywhere else.

06Fleet & performance, for senior developers

Everything so far serves two readers: someone building a spider, someone reviewing one. Neither view answers a question a team lead actually has — across every spider this cohort has shipped, what's healthy, what's stale, and is the docs platform itself fast? That's a third audience, and it's a different job: fleet-wide visibility, not single-spider QA.

Correction — this is by design, not unfinished

components/scrapers/ScrapersTable.tsx already defines Status and Last Run columns (fields last_run_status and last_run) on the spider list, and lib/scraper-data.ts's SpiderEntry type declares both fields, but listScrapers() only ever returns { slug }. It looks half-built and never finished. The Meetings Viewer spec says otherwise, explicitly (§5.4, "Local fields explicitly out of scope"): agency, last_run, and last_run_status are deliberately unpopulated in local mode — "no local mechanism produces or stores them." The placeholder isn't a gap. It's the local half of a shape whose other half is Production mode (§4.2 of the spec: "The shape supports adding optional fields … in production without breaking the local consumer").

Real fleet data waits on Production mode — it isn't a local workaround

That correction changes the plan, not just the framing. §3's diagram already shows two things that aren't the Documenters.org production pipeline: local mode and the viewer's own planned Production mode. Fleet data belongs on the second one, not invented locally:

  • The real source is Production mode's manifest.json, fetched the same way the viewer's own production mode will (§3's spec citation) — raw.githubusercontent.com, no backend. A local mtime-and-self-check substitute would directly contradict the spec's §5.4 and §7 — considered and scrapped, not built.
  • This gates the fleet KPI panel on Production mode shipping (§8's flagged, not-scoped-here app feature). Until then, /docs/analytics's fleet panel ships as an honest empty state — "waiting on Production mode," not a fabricated local number.
  • The Airtable-backed alternative is now weaker, not just bigger scope — beyond the write-scoped PAT needing a server-only Route Handler, that handler would be an application-managed API server, which the spec's §7 lists as an architectural invariant that "should not be broken without explicit revisit." Production mode's static-file fetch doesn't have that problem. Prefer it once it exists, rather than building a second, invariant-breaking path to the same data.

The other half: is the docs platform itself fast?

§1.2 deferred axe-core + Lighthouse CI for having no place to show results. This tab is that place — the condition is now met, so it's back on the roadmap (§8, P7), scoped tightly: Lighthouse CI writes one JSON artifact per build; this page renders it. No new runtime dependency, no telemetry service, nothing that phones out from a user's browser.

07Agents, memory & skills

A new category, deliberately started thin: a shared place for how teams use AI coding agents effectively — not just CTD, but the frontend team on this repo, whoever owns the scraper repos, whoever owns the CI/CD automation in §3's /pipeline, and any team that comes after. The goal is the same one behind everything else in this playbook: less duplicated tribal knowledge, less onboarding by osmosis. The difference here is that almost none of the content exists yet — so this section is a method for growing it team by team, not a finished IA to fill in.

Where this repo actually stands today

One file: AGENTS.md, one rule (a warning that this app's pinned Next.js version has breaking changes versus a model's training data). No .claude/skills/, no .claude/agents/, no hooks. That's the honest starting point — nothing below invents practices this repo doesn't have yet.

The vocabulary — four mechanisms, one job each

Mechanism Lives at For In this repo, today
Memory AGENTS.md / CLAUDE.md, repo root Standing context every agent session in this repo loads automatically — the guardrails you'd otherwise repeat in every prompt One rule (above)
Skill .claude/skills/<name>/SKILL.md A packaged, reusable procedure — a checklist or workflow invoked by name mid-session, not repeated from memory each time None yet
Subagent .claude/agents/<name>.md A specialized persona with its own tool access, for a recurring task worth a dedicated role — a reviewer, a researcher None yet
Hook .claude/settings.json An automated action on a session event — run a formatter after every edit, block a risky command None yet

The decision method is short: something every session must always know → memory. A procedure you'd explain the same way every time → a skill. A distinct role worth its own context and tool scope → a subagent. Something that should happen automatically, unasked → a hook. Most teams starting out will only ever need the first two.

The method: how a team adds its own section

  1. Write down one real thing, not a speculative one. The smallest actual convention your team already applies with an agent — not an aspirational list of everything a well-run team's agent setup could someday include. This playbook's own rule against building for hypothetical readers (§1) applies here too.
  2. The real file lives in your team's own repo, not here. An agent session working in city-scrapers-core only ever reads that repo's AGENTS.md and .claude/ directory — nothing hosted only in city-scrapers-meetings-viewer's docs is ever loaded by a session working elsewhere. Put the actual memory/skill/agent/hook file where it will actually be read.
  3. This site links to it and summarizes intent in two or three sentences — never a copy. Same reasoning as §1.3: a duplicate goes stale the moment the source changes and nobody notices. A link can't drift out of sync with itself.
  4. List it on /docs/agents's team table and open a PR the same way your team reviews anything else.
Lighter governance than §3's PDW/CB content — with one exception

Section 09 raises a real open question about who can correct content describing PDW/CB's own process, because they don't have git access to this repo. For most of this section that doesn't apply: every team it's written for — scrapers, this app's frontend team, whoever owns CI/CD — already has git access to their own repo, and the only discipline needed is link-not-duplicate, above.

The exception is §7.1's code-review skill, which PDW owns. The page describes it and links to it; it must not restate its checklist or imply CTD maintains it. Link plus a two-sentence summary of intent — step 3 of the method above — is the whole treatment.

7.1 Two skills already exist — the stub was wrong

The tree below listed scrapers.mdx as a stub owned by another team. That's now out of date: two real skills exist, they're already in use, and together they cover both ends of the scraper lifecycle. This becomes the section's most substantial page rather than its emptiest.

Spider Development skill Code-review skill
Owner CTD PDW
When it fires While writing a spider — build, refactor, debug After the PR opens — standalone or a GitHub Actions check
Shape Prescriptive: seven spider types with code, required standards, API patterns (CivicClerk, Legistar, Diligent, Drupal), anti-blocking recipes Evaluative: review mindset, a process, a large reference checklist, output-validation tables

Two skills at two lifecycle stages is a genuinely good split, and worth documenting as the recommended shape for any team that adds its own: one skill that helps you write it, one that checks what you wrote, and no overlap between them. That's the reusable lesson /agents exists to carry.

Defect, worth fixing before this page cites it

The Spider Development skill's frontmatter still carries the template placeholder: description: A brief description, shown to the model to help it understand when to use this skill. Paired with trigger: model_decision, the description is the only signal the model has for when to load it — so as written, it either never fires when it should or fires when it shouldn't. The skill's own body has the real description in its first line ("Use this skill when building, refactoring, or debugging Scrapy spiders for city-scrapers projects"); it just needs to move up into the frontmatter. One-line fix, and it's the difference between a skill that works and one that's installed but inert.

There is a third skill, and a pipeline this platform should not duplicate

An external review document names a test-and-verify-scraper-outputs skill in development, and an anomaly detection system that is Phase 1 of something called the Scrapers Stability System. It also states the target shape: a three-step automated pipeline — code-review check, spider output verification, staging deploy.

That matters here for one reason. <RubricReport> (§4.2) validates a spider's JSON output against the schema, and step 2 of PDW's pipeline validates a spider's output against the schema. Those are the same check in two places, built by two teams, and neither knows about the other yet. <RubricReport> is still worth building — it's interactive, runs in the browser on a file you paste, and serves a QA reviewer rather than a CI job — but it should be scoped deliberately as the human-facing half and share §5's generated constants with the automated half, not grow into a second implementation of it. Raise this with PDW before P3 rather than after.

Skills cite the docs; they don't restate them

Both skills currently carry their own copies of facts the docs also publish — the meeting schema, the status and classification constants, the lint and test commands, the validation checklist. Section 02 is what that costs: copies drift from constants.py, and one of them will fail a correct spider in CI. The rule that prevents a repeat is the mirror of §7's link-not-duplicate rule, pointed the other way:

The docs hold the facts; the skills hold the judgment

A skill should carry procedure, heuristics, and worked examples — the things that are genuinely its own. For anything enumerable and generated (schema fields, constants, commands, the QA rubric) it should link to the doc anchor instead of restating it. That's only workable because the site publishes per-page .md routes and llms-full.txt (§4.2): an agent can follow the link and read the canonical text directly. This is the concrete answer to "we want agents reading our docs to give developers feedback" — the docs stop being a copy of the skill and become the thing the skill defers to.

Two consequences worth building for. First, <RubricReport> (§4.2) and PDW's review checklist are validating the same output against the same rules — both should read §5's generated constants, so a fix in city-scrapers-core reaches the interactive checker and the CI reviewer at once. Second, treat agent-readability as a page requirement rather than a nice-to-have: a page restating a source that agents can't read has to be reachable as clean Markdown itself, or it inherits the defect it was created to fix.

09Open questions for round two

Platform-build questions only. Each one changes what gets coded, and each is answerable without settling any content dispute. Questions about whether a source's content is correct are parked for the third research round (see the roadmap's R3 entry) and are deliberately absent here.

Blocking — needed before P2 starts

  • Which paths get which owners in CODEOWNERS? Routing is the whole point of section 02, and it resolves against this file. It needs real teams or usernames with write access — a placeholder routes nothing. Merge history suggests a small group already performs merges; confirming who should be paged for docs paths is a five-minute conversation that unblocks the phase.
  • Where do findings surface first — PR comment, dashboard, or both? All three outputs come from one record, so this is about which ships in P2 versus P6. A PR comment reaches a developer at the moment of change; a dashboard is better for standing state. Recommendation: PR comment in P2, dashboard deferred to P6.
  • What is the fixture corpus, concretely? Section 02.6 needs documents with known disagreements to measure recall and precision against. Any set of real program documents works — the requirement is that a human has already read them and knows what the detector should find.

Needed before P4

  • Does a Keystatic edit open a PR or commit directly? Undocumented, and it decides whether editor changes pass through the conflict reporter at all. If they commit directly, the two need wiring together before the editor ships.
  • Do editors need repository write access, or a hosted tier? The self-hosted path is free but requires every editor to hold write access. This is a platform-capability question with a cost attached, not a content question.

Worth deciding, not blocking

  • Does /docs need a program-level frame? The site presents as one application's manual. If readers outside this repo are expected, a header breadcrumb or a distinct docs masthead resolves it far more cheaply than a rename. Purely a presentation decision.
  • How is a false positive muted? The finding record carries a stable id for exactly this. What's undecided is where the mute list lives and who can add to it. Getting this wrong is the most likely way the reporter gets ignored.
  • Should the conflict dashboard be public? It reports that organizations' documents disagree. That's useful internally and potentially awkward externally. Worth an explicit answer before section 06's analytics surface ships.

10R3 analyses

The roadmap's R3 entry parked four questions because none of them changes what gets coded in round two — but each still benefits from written analysis before the third research round picks them up. What follows is not a decision record; it is the shape of each problem, the options on the table, and the recommendation this playbook would defend. Nothing here is implemented.

Content-conflict resolution policy

The reporter detects that two documents disagree and routes the finding to an owner. What it deliberately does not do is decide who is right when neither side is executable code — two prose sources can contradict each other with no constants.py to arbitrate. Today that produces a likely-confidence finding that sits open until a human settles it.

Options:

  • Escalation ladder. The finding's owner proposes a resolution naming both sources; the counter-document's owner confirms or disputes; unresolved findings escalate to the program manager after a fixed window. Cheap, uses the ownership routing that already exists.
  • Precedence by source class. The taxonomy already orders executable > structured > synced > git-prose > external, and it could break prose-vs-prose ties by preferring the more recently synced mirror. Tempting, but it encodes "newest wins" — a stale upstream doc corrected yesterday beats a fresh copy of a wrong one only by accident.
  • A standing docs council. Correct authority, far too heavy for a program of this size.

Recommendation: the escalation ladder, plus one platform-side change — an ageing signal on /docs/conflicts so an unsettled finding gets louder with time rather than becoming furniture. The platform's job is to make inaction visible, never to pick a winner: a tool that silently resolves a content dispute teaches the program to trust it less, not more.

Source-of-truth consolidation

The same fact is currently restated across Google Docs, PDFs, upstream repos, skills, and this site. The question is whether the program should reduce the number of places a fact lives, or keep the mesh and police it.

Options:

  • Consolidate into this platform. One place for everything — but the migration cost is real, and several source owners don't have git access to this repo, so consolidation would strand them.
  • Master-per-fact, link-not-duplicate. Every fact keeps exactly one master; everything else links to it or renders from it. This is already the de facto policy — sources.json names origins and TTLs, and the claim registry names a master for every checked fact.
  • Hybrid. Consolidate only enumerable facts (vocabularies, schema fields, command lists) into generated artifacts; leave stable prose distributed.

Recommendation: adopt the hybrid as the stated policy, because it is already load-bearing — the generated schema is a consolidated enumerable fact, and constants.py is the vocabulary master everything else defers to. Formalising it turns an emergent pattern into a rule a new team can be handed in one sentence: one master per fact; generate or link, never copy.

Cross-organization editing authority

Pages on this site describe processes owned by teams outside CTD — PDW's review skill, City Bureau's framework. Those teams hold no git access to this repo, so when their process changes, the page describing it is written by the wrong hands.

Options:

  • Grant external repo access. Works technically; fails organisationally — write access to CTD's repo for occasional doc corrections is a permission grant nobody should want to maintain.
  • Hosted Keystatic tier. Moves editing authority out of GitHub permissions entirely; resolves the §9 question about editor access at the same time. Real cost, real vendor dependency.
  • Correction intake. An issue template or contact path where external teams file corrections and a repo maintainer applies them. Zero access granted; latency measured in days.
  • Shrink the surface. The stronger version of the fix: pages about another org's process hold a link plus a two-sentence summary — the §7 rule — so most corrections happen at the source and never need to reach this repo at all.

Recommendation: shrink the surface first, intake second. If corrections still arrive faster than a maintainer can apply them, then the hosted tier has earned its cost — not before. The drift engine already tells you when an external process page is stale; the intake path is what turns that signal into a fix.

Scraper-domain content review

The drift engine verifies that documents agree with each other. It cannot verify that what they agree on is correct — whether the spider guidance describes what actually works against real agency sites. That judgment needs scraper-domain expertise this round does not hold.

Options:

  • Periodic expert review. A named reviewer per content section, on a cadence, recorded in frontmatter — last_verified already exists as a convention in the mirrored PDW skill, which suggests the upstream teams think this way too.
  • Surface the review state. Render last_verified on the page so a reader can see whether guidance is six days or six months stale before they trust it.
  • Let drift findings drive review. A conflict already forces a human to re-read both sources — review happens as a side effect of detection.

Recommendation: all three, in that order of effort. The frontmatter field plus a rendered badge is an afternoon of work and converts "is this page still true?" from a guess into a displayed fact. Correctness remains a human process — the platform's contribution is making the review state visible, the same job it does for disagreement.

Common thread

All four parked questions resolve to the same division of labour the platform already embodies: humans own judgment, the platform owns visibility. Wherever an R3 answer drifts toward "the platform decides" — picking a winner, choosing a master, declaring content correct — it has drifted off the design.
